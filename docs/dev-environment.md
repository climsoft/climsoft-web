# Climsoft Web Development & Deployment Environment

The reasoning behind how the dev, test and prod environments are wired: what each Compose file is for, why nginx fronts everything even in dev, how configuration is resolved, and why Superset lives on its own hostname.

## The three Compose files

There are three Compose files, one per stage. Dev and test/prod containerize the API and PWA differently, through separate Dockerfiles, because they serve different purposes: dev optimizes for hot-reload, while test/prod build the image that actually gets deployed.

- **`docker-compose.dev.yaml`**: everything runs in containers, including the API and PWA, using `back-end/api/Dockerfile.dev` / `front-end/pwa/Dockerfile.dev` (separate from the production `Dockerfile`s). These bind-mount the source tree into the container and run `nest start --watch` / `ng serve --host 0.0.0.0`, so edits on the host hot-reload just as they would running natively. A named volume shadows `node_modules`, so `npm ci` isn't rerun on every start and container-native builds (e.g. `bcrypt`, `@duckdb/node-api`) aren't clobbered by a host `node_modules`.
  - `climsoft_nginx_proxy` (`nginx.dev.conf`, default port 8080) fronts the API, Superset and the PWA. It is built from the repo-root `Dockerfile.dev`. Unlike the API/PWA `Dockerfile.dev`s, this one doesn't bind-mount source, because there's only config, no source to reload. It just sets up the same envsubst-on-templates env vars as the production nginx `Dockerfile`. `nginx.dev.conf` itself stays bind-mounted, so config edits take effect on a container restart, with no rebuild.
  - It also runs Postgres/PostGIS (`climsoft_db`), the four adapter runner containers (behind the `adapters-python`/`adapters-r`/`adapters-javascript`/`adapters-duckdb` profiles), and Superset (redis, init, server, worker, beat, all five behind a `superset` profile).
  - Every var it references is required: there are no inline `${VAR:-default}` fallbacks, matching test/prod. An incomplete `.env` fails loudly instead of silently substituting a value you didn't choose.
- **`docker-compose.test.yaml`**: builds the API and PWA from local source using the *production* Dockerfiles (`context: ./back-end/api`, `./front-end/pwa`, no `.dev` suffix) plus the production `nginx.conf` reverse proxy. This tests the containerized build and deploy path close to production without needing published images. There are no bind mounts and no hot-reload: it is the artifact that would actually ship, just built locally.
- **`docker-compose.prod.yaml`**: same shape as test, but pulls prebuilt published images (`climsoftdevelopers/climsoft-api:*`, `climsoft-pwa:*`, `climsoft-nginx-proxy:*`, `climsoft-superset:*`) instead of building from source.

Neither the API nor the PWA uses an entrypoint script any more. The API validates its own required env vars in `app.config.ts` (`requireEnv`, which fails loudly at module load). The PWA's `assets/config.json` is synthesised by nginx itself (in both `nginx.conf` and `nginx.dev.conf`), not generated by a container-startup script.

## Dependencies and the `node_modules` volume

Running `docker compose exec ... npm install` only patches the running container's volume, not the image. Host-side editor tooling (VSCode's TS/ESLint) can't see the container's volume at all. That's why a dependency change has to be applied in three separate places (see `CLAUDE.md`).

Rebuilding the image alone does **not** update an *already-running* container. The named `node_modules` volume only seeds itself from the image's `node_modules` layer the first time it's created, while it's empty. Once it exists, it shadows whatever is newly baked into the image on every later start. This is the same mechanism that lets it survive container restarts in the first place.

## Configuration (`AppConfig`)

`AppConfig` (`back-end/api/src/app.config.ts`) has no dev/prod distinction and no code-level defaults for anything environment-specific. `AppConfig.devMode` was removed; it existed only to work around the API running natively on Windows, which is no longer a supported dev setup. Every setting reads straight from `process.env` with a bare `!` assertion, so `docker-compose.dev.yaml` sets each of `DB_HOST`/`PYTHON_RUNNER_HOST`/etc. explicitly to the container service names (`climsoft_db`, `climsoft_python_runner`, ...), the same way test/prod do.

The API has no `dotenv`/`ConfigModule`, so `.env` is only ever loaded by Docker Compose's own `environment:` injection, never by the Nest process itself.

The two exceptions to "no in-code defaults" are `adapters.maxUploadSizeBytes` and each adapter runner's `timeoutSeconds`. No compose file (dev/test/prod) ever sets these, so they keep an in-code default rather than becoming a required var nobody sets.

## Why nginx sits in front of the API (and PWA) in dev too

The production `nginx.conf`'s `/api/` location carries request-handling behavior that the API's own code doesn't replicate: `client_max_body_size`, streaming (`proxy_request_buffering off`/`proxy_buffering off`), and timeouts. A request sent straight to `climsoft_api:3000` bypasses all of that. In the past this let bugs like an upload-size-limit bypass go unnoticed until `docker-compose.test.yaml` or later.

`nginx.dev.conf` is a trimmed copy of `nginx.conf` with the same `/api/` block and Superset server block, plus a `location /` that proxies to `climsoft_pwa:4200` (`ng serve`) instead of serving a static build; dev never builds the PWA. `climsoft_pwa` also stays directly published on 4200 as a fallback that bypasses the proxy.

Because the PWA and API share nginx's origin in both dev and prod, `app-config.service.ts` always resolves `apiBaseUrl` from `document.location.origin`. The old `isDevMode()` branch (hardcoded `localhost:3000`/`8088`, bypassing nginx) has been removed.

The `/api` prefix comes from `app.setGlobalPrefix('api')` in `main.ts` and nowhere else. nginx's `/api/` location forwards the path unchanged, with no rewrite.

## Superset

### Profile vs. `SUPERSET_ENABLED`

Superset's five containers (`climsoft_superset_redis`/`_init`/`_superset`/`_worker`/`_beat`) sit behind a `superset` compose profile in all three compose files, the same pattern as the adapter runners' `adapters-*` profiles. This is a *separate* toggle from `SUPERSET_ENABLED`: the profile controls whether the containers start at all, and the env var controls whether the API/PWA treat Superset as available. Nothing keeps the two in sync automatically (the same is true of `PYTHON_RUNNER_ENABLED` and `adapters-python`). Setting `SUPERSET_ENABLED=true` without the profile active means the API will try to reach a Superset that was never started.

`climsoft_nginx_proxy` deliberately has no `depends_on` on `climsoft_superset`, because Compose refuses to start a service that hard-depends on one excluded by profiles. Instead it returns proxy errors on `SUPERSET_HOSTNAME` until those containers are up, the same tolerance it already has for the equally optional runners.

`SUPERSET_HOSTNAME` stays required in `.env` whether or not the profile is used. nginx substitutes it into a `server_name` directive at container start. An empty value there is a config *parse* error, not just a proxy failure, so it would take down the whole nginx container, not only Superset's origin.

### Why its own hostname, not a path prefix

An earlier `location /superset/` nginx block (stripping the prefix before forwarding) doesn't work. Superset's frontend emits absolute root-relative URLs: static assets, API calls, its embedded-dashboard route. Separately from that, a few of Superset's own core views, like `/superset/welcome/`, hardcode that prefix into their Flask route regardless of proxy config. As a result, nginx can never consistently strip or preserve the prefix correctly for all of them at once. The Superset maintainers' own guidance is to use a subdomain, not a path prefix, for exactly this reason ([apache/superset#29547](https://github.com/apache/superset/discussions/29547)).

So `nginx.conf`/`nginx.dev.conf` give Superset a second `server {}` block matching `server_name ${SUPERSET_HOSTNAME}`. It uses the same port as the main app: it's the same nginx, told apart by the `Host` header. That block proxies straight through to `climsoft_superset:8088` with no path rewriting. `climsoft_superset` is not published on the host in any compose file; it's only reachable through nginx, which closes the same request-handling bypass that routing `/api/` through nginx closed.

`SUPERSET_HOSTNAME` is a bare hostname: `superset.localhost` in dev (modern browsers resolve it to loopback automatically, with no `/etc/hosts` edit) or a real DNS subdomain pointed at the same host/load balancer in production. It's substituted into both nginx configs via envsubst at container start. The official nginx image's `docker-entrypoint.d/20-envsubst-on-templates.sh` does this automatically. `./Dockerfile` (the test/prod nginx image) points `NGINX_ENVSUBST_TEMPLATE_DIR`/`NGINX_ENVSUBST_OUTPUT_DIR` at `/etc/nginx` so it processes `nginx.conf.template` in place, and `docker-compose.dev.yaml` does the same via `environment:`.

### How the PWA finds Superset

`app-config.service.ts` can't derive `supersetBaseUrl` from `document.location.origin` the way it does `apiBaseUrl`, because Superset is on a different origin. Instead it fetches `/assets/config.json`. This is not a real file in the PWA's build output: both nginx configs' `location = /assets/config.json` block generate it on the fly, using the same `SUPERSET_HOSTNAME` substitution as the Superset server block. The PWA combines the returned hostname with the current page's protocol and port, which are always correct because it's the same nginx, same port and same scheme, just a different `Host` header.

This fetch is deliberately *not* awaited before Angular bootstraps in `main.ts`. An earlier version (`git log` on `front-end/pwa/src/main.ts`) blocked `bootstrapModule()` on a config fetch with no `.catch()`, so a failed or offline fetch left a permanently blank screen. `getSupersetBaseUrl()` returns a `Promise<string>` (resolving to `''` on failure) instead. Only two call sites use it: `product-viewer.component.ts`'s dashboard embed and `view-climate-products.component.ts`'s "open Superset" button. Both are user-triggered well after bootstrap.
